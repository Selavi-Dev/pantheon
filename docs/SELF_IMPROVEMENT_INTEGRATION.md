## Bounded operating procedure

1. Use only authorized outcome evidence, including existing Grokbot reports. Hermes deduplicates against open proposals, canonical routine purposes and Grokbot ownership. Argus observes; Socrates challenges causes and assumptions; Athena prioritizes alternatives.
2. Mnemosyne prepares an attributed lesson with stable proposal ID, evidence references, classification and hypothesis/review status. Obsidian is draft improvement memory only. With no explicitly authorized designated inbox access, return a draft for an operator; do not invent a live vault path. Never overwrite notes, export automatically, promote unvalidated claims, copy secrets or perform global vault edits. The `lesson` command needs no vault write access; an explicitly authorized operator may use `export-lesson` to a private designated inbox.
3. Hephaestus may prepare a minimal candidate and comparable tests in an already authorized isolated branch or sandbox, with rollback. This produces a draft for review. At most one candidate and one iteration are permitted per run; stop on missing evidence, budget or authority. Existing sandbox/tool restrictions still apply.
4. Argus evaluates independently; candidate authors recuse from independent verification. Themis reviews provenance, regressions, permissions and Grokbot overlap. Hermes assembles one decision packet; Apollo drafts reports from verified findings. No agent approves production changes or sends a report through this workflow.
5. An authenticated administrator separately approves the exact candidate SHA-256 and scope before a separately authorized production deployment. Production SOUL, model routing, tool grants, governance, schedules and configuration remain approval-gated. Explicitly authorized draft source preparation does not require a second approval merely because it is reviewable source; it grants no production authority.

## State and approval trust boundary

Keep local workflow state in a restricted private location outside the source repository, with one trusted writer. The JSON store is a review aid, not a distributed ledger: records are not signed, authenticated or tamper-proof. Map provenance explicitly to the base ledger where supported; neither local store authenticates users or dispatches work. Do not expose approval-recording access to agent tools. Local tests are necessary but do not prove deployment enforcement.

The local CLI supports `approve ID FILE.json` after passing independent evaluation and Themis review. The file contains `administrator` (authenticated operator identifier in your external system), `candidate_sha256`, `decision` (`approve` or `reject`), `scope` (exact proposal scope), and `evidence_ref` (reference to the authenticated approval record). No CLI mechanism authenticates that identity. Restrict filesystem and invocation access; never treat local approval as an authorization token. No synthetic approval fixture is distributed. Candidate or scope changes require new evaluation and approval.
